# RCA — consultation-astro (plume-astrale.fr) : 404 global `/api/*` + login cassé après déploiement

## TL;DR
Le backend prod **démarre et sert `/api`** — ce n'est PAS un crash global ni un secret manquant. Deux phénomènes distincts se cumulent :

1. **Fenêtre transitoire post-deploy (~4 min)** : le pod backend met longtemps à devenir *ready* (probes en 503 / `connection refused`, nginx `upstream timed out → 127.0.0.1:8001/health`). Pendant cette fenêtre, nginx renvoie 502/503 sur TOUTES les routes `/api/*` → vécu par l'utilisateur « juste après le déploiement, tout tombe ». Cause : la régénération synchrone de 12 PDF horoscope via GPT (`horoscope_scheduler` / `build_daily_horoscope`) au startup bloque la réponse de `/health`.
2. **404 persistant, spécifique à certaines routes (cause racine du login cassé)** : le backend qui tourne **n'enregistre PAS** certaines routes, alors qu'il en sert d'autres.

## Preuves collectées côté prod (run actif f23957df, avant redeploy)
Sondes directes sur le domaine backend `https://consultation-astro.emergent.host` :
- `GET /api/` → **200** `{"name":"Plume Astrale API","status":"ok","version":"v3"}`
- `GET /api/health` → **200** `{"ok":true,"service":"plume-astrale-api"}`
- `GET /api/admin/preview/theme-natal-v3` → **401** `{"detail":"Authentication required"}` → **route NOUVELLE bien montée** (admin_preview_v3)
- `GET /api/auth/supabase/me` (endpoint de login) → **404 `{"detail":"Not Found"}`** → **404 généré par FastAPI lui-même**, donc la route n'est **pas enregistrée** dans le process qui tourne
- `GET /api/natal-print-bump/` → **404 FastAPI** (natal_lulu_bump non monté — au moins sur le path testé)

Conclusion : le backend est vivant (sinon `/api/` et `/api/health` ne répondraient pas 200). Le 404 du login est un **404 applicatif** = route absente de l'app montée, pas un problème d'ingress/nginx/secret.

## Cause racine (confirmée côté prod)
Le backend buildé et démarré **n'enregistre pas le router d'auth Supabase** (`/api/auth/supabase/me`) ni le router `natal_lulu_bump` (`/api/natal-print-bump/*`), alors qu'il enregistre bien `admin_preview_v3` (`/api/admin/preview/theme-natal-v3`). 

Comme le build a réussi et que le process démarre (donc pas d'`ImportError` dur bloquant uvicorn), le pattern le plus probable est une **inclusion partielle des routers dans `server.py`** : par ex. un `include_router(...)` encapsulé dans un `try/except` qui avale une exception levée lors du montage de `natal_lulu_bump` (routes/natal_lulu_bump.py) et saute les `include_router` suivants (dont le router auth), OU un ordre de montage qui fait qu'une erreur sur un nouveau router court-circuite les autres. Le fait que `admin_preview_v3` (monté) fonctionne mais que `auth` + `natal_lulu_bump` soient absents cadre avec une interruption au milieu de la séquence `api_router.include_router(...)`.

> Je n'ai pas pu reproduire statiquement dans le sandbox eph : `spawn_eph_pod` a échoué (`eph_spawn_terminal`, limite mémoire 2Gi — archive source trop volumineuse). La cause ci-dessus est donc **confirmée par le comportement prod** (404 FastAPI sélectif) mais **non reproduite en sandbox**.

## Actions correctives
### Code (E1 — à appliquer dans la source preview puis redéployer)
1. **`server.py`** : auditer le bloc `api_router.include_router(...)`. Retirer tout `try/except` silencieux autour des inclusions, OU isoler chaque `include_router` pour qu'un échec sur un router n'empêche pas les suivants. Vérifier que le router d'auth Supabase (`/api/auth/supabase/me`) ET `natal_lulu_bump` sont bien inclus **inconditionnellement**. Vérifier les imports de `routes/natal_lulu_bump.py` (dernier ajout) — une exception à l'import/au montage de ce module est le suspect n°1 qui fait sauter les inclusions voisines.
2. **Startup non bloquant** : déplacer la régénération des 12 PDF horoscope (`horoscope_scheduler` / `build_daily_horoscope`, appels GPT) hors du chemin de démarrage synchrone (tâche de fond / après `startup`), pour que la readiness probe `/health` réponde immédiatement. C'est ce qui a provoqué la fenêtre d'indisponibilité ~4 min (502/503 sur tout `/api/*`) juste après le déploiement.

### User / E1 (vérification)
3. Confirmer que `REACT_APP_BACKEND_URL` (Deployment Panel → Secrets) pointe bien sur le domaine prod (`https://plume-astrale.fr`) avec préfixe `/api`, et pas sur une URL preview.
4. Après correction du code + redeploy, **re-tester** `GET /api/auth/supabase/me` (doit renvoyer 401/200, plus 404) et `GET /api/natal-print-bump/*`.

## Important — portée du redeploy que je viens de lancer (run c4d33748)
Le redeploy a **repassé la pipeline au vert** (build + health_check `/health`). MAIS le health_check ne sonde que `/health`, qui était **déjà vert** avant. Un deploy vert **ne garantit donc pas** que `/api/auth/supabase/me` est de nouveau enregistrée : si la source preview contient toujours le même `server.py`, le router d'auth restera absent. Il faut re-tester les routes ci-dessus ; si elles sont toujours en 404, le fix code (action 1) est nécessaire — un simple redeploy de la même source ne corrigera pas la cause racine.
